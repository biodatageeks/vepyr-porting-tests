# Dynamic vepyr version resolving

`PINS.toml` pins the annotation corpus (see [dataset-pins.md](dataset-pins.md)).
The **engine** — vepyr and its dependency ladder — is deliberately *not* pinned in
this repository. It is a run-time parameter: `./run_tests --vepyr REF`, or, when the
flag is omitted, `biodatageeks/vepyr`'s current `master` HEAD.

This document describes end to end what `./run_tests` does with that ref, so the
mechanism can be understood without reading `tools/run_tests/engine.py` or a PR
thread. Implementation: `tools/run_tests/engine.py`; call site:
`tools/run_tests/cli.py::_run_data_tests`.

## Why a resolve flow at all

The committed `Cargo.toml` of this repository floats on `biodatageeks/vepyr`
`master`. A data-test must nevertheless be able to state *exactly* which engine
revision it ran against, and a CI or bisect run must be able to ask for a specific
one. Two problems follow:

1. A ref (`0.7.0`, `master`, `a1b2c3d`) is not evidence — a 40-char sha is.
2. vepyr does not vendor its own ladder. The revisions of
   `datafusion-bio-functions` (dfbf) and the `datafusion-bio-format-*` workspace that
   a given vepyr revision compiles against are named by **that revision's own**
   `Cargo.toml`. Taking them from *this* repository's lockfile would test a ladder
   nobody ships.

So the flow reads the engine revision's own manifest and reproduces its ladder
locally, via cargo path `[patch]` tables.

## The stages

### 1. `gh api commits` — REF → sha

`engine.validate_ref` first rejects anything that is not a plausible git ref
(charset, length). Then `engine._resolve_sha` calls

```
gh api repos/biodatageeks/vepyr/commits/<REF>
```

and takes `.sha`. GitHub dereferences branches, tags and abbreviated shas for us, so
one call covers all three forms. The full 40-char result is what the run summary
prints as `vepyr sha`, and it is the value a ledger entry should quote as evidence.
A ref that does not resolve exits `6` (engine resolve/checkout failure).

### 2. `gh api contents` — read the engine revision's own pins

`engine._read_cargo_toml` calls

```
gh api repos/biodatageeks/vepyr/contents/Cargo.toml?ref=<sha>
```

base64-decodes `.content` and parses it with `tomllib`. From
`[dependencies]` it extracts, via `_dep_spec` / `_git_rev`, the `git = URL` plus the
`rev` / `tag` / `branch` of:

- `datafusion-bio-functions` (dfbf), and
- the formats ladder, read from the `ensembl-cache` entry with the `vcf` entry used
  as a cross-check — if the two name different `(url, rev)` pairs the run stops
  rather than patch an inconsistent ladder.

Note what is pinned here: whatever the *engine revision* says, which is always a
public `biodatageeks` crate. Nothing in this flow substitutes a different repository
for the one the manifest names, and no `test-internals` overlay is applied.

### 3. Clone dfbf + formats

`engine._checkout_repo` materialises each of the two repositories under the source
root (`$RUN_TESTS_SRC`, else `<repo>/.run_tests/src` — see `engine.default_src_root`):

- a `--mirror` clone is kept once per repository and re-fetched, so repeated runs do
  not re-download history;
- each resolved revision then gets its **own immutable worktree** at `<repo>/<sha>`,
  which means two runs against two engine revisions never fight over one checkout.

### 4. `engine.toml` patch table

`engine.engine_toml` renders a byte-stable cargo config:

```toml
# generated by ./run_tests — engine path-patch config
[patch."<dfbf git url>"]
datafusion-bio-function-vep = { path = "…/<dfbf sha>/datafusion/bio-function-vep" }

[patch."<formats git url>"]
datafusion-bio-format-core = { path = "…/<formats sha>/…" }
datafusion-bio-format-vcf  = { path = "…/<formats sha>/…" }
…
```

**Every** crate of the formats workspace is patched, not just the two named in the
manifest: they depend on one another, and patching a subset would link two copies of
the same crate at different revisions. `engine.materialise` writes the rendered text
to `<repo>/.run_tests/engine.toml` and returns its path.

### 5. `cargo update` / `cargo test`

The config is handed to cargo as `--config <path>`:

```
cargo test --no-fail-fast --config .run_tests/engine.toml --test data_… [--test …]
```

There is no explicit `cargo update -p …` pre-step (issue #21). With the `[patch]`
path tables present in the `--config` file, cargo re-locks the patched packages by
itself on the next resolve; an extra `cargo update` would only re-resolve the same
graph and cost a round trip. The effect on `Cargo.lock` is the same — which is why
stage 6 exists.

### 6. `LockGuard` restore

Patching rewrites the checked-in `Cargo.lock`, and that rewrite must not survive the
run. `engine.LockGuard.held()` wraps the cargo invocation:

- on entry, in a git checkout where `Cargo.lock` is tracked, it runs
  `git checkout -- Cargo.lock` — which also **sweeps a rewrite left behind by an
  earlier killed run**, so recovery needs no manual step;
- on exit it restores the same way.

Restoration goes through git rather than an in-process snapshot precisely because the
pristine copy then lives in the index and survives a `SIGKILL` or an OOM kill that
skips every `finally` block. Outside a git checkout, or when `Cargo.lock` is
untracked, the guard falls back to an in-memory snapshot — the best that can be done
there.

## Consequences worth knowing

- **The default ref floats.** Omitting `--vepyr` tests `master` HEAD *as it stands at
  that moment*; a run today and a run tomorrow can exercise different engine code.
  The summary always prints the resolved 40-char sha, so the run is at least
  *identifiable* after the fact — but pass `--vepyr REF` for anything that must be
  reproducible.
- **`Cargo.lock`'s package count is the real transitive closure** of the annotate
  engine plus its ladder — it is large because the ladder is large, not because
  anything spurious is vendored.
- **`gh` must be authenticated.** Both API stages go through `gh api`.
